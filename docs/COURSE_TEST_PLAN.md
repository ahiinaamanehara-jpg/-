## 3. 実行する技術テスト

追加する出力制御の検証では、参考画像・下絵・教材に識別できる色や模様を入れ、内部のサムネイル・工程記録や許可されたPNGへ混ざらないことを画素で確認する。それに加え、教材の画素が入っていない場合も、なぞった作品をPNG取得・端末共有できないことを制作・詳細・専用画面・保存失敗時に検証する。作品取込、コピー、下絵解除、レイヤー、旧データ、ZIPでも利用範囲を保つ。現在の全データZIPが対象画像を含むことと、スクリーンショット・配信画像の取得まで完全には防止できないことを、UIの説明と照合する。

- 単体：教材の工程ID・版、現在工程の解決、3段階ヒント選択、閲覧／実践／スキップの区別、未知データ、入力上限、バックアップ形式と参照。
- 結合：実ブラウザーのIndexedDBで、作品・工程・画像の原子性、revision、独立した工程PNG、移行・関連削除・復元を確認する。モックだけで保存完了としない。
- 画面：PlaywrightでL01〜L22の対象部分を検証する。画面切替前後のCanvasの同一性と画素、保存前後の画像、ZIP中のBlob・寸法・利用範囲も確認する。
- 回帰：既存の推し・テーマ・自由創作、任意の下絵／レイヤー、1:1・3:4・4:3・参考画像比率、拡縮回転・専用画面・ボタン非表示、PNG／ZIP・質問のスキップを保つ。
- 静的確認：実装した工程に合わせ、型チェック・lint・単体・関連／全体E2E・本番ビルドを実行する。ブラウザー共通操作はChromium・Firefox・WebKitで確認し、実機と区別する。
- 保存の待機はアプリのPNG準備と既存の保存確認条件に合わせる。失敗を自動再試行・比較許容値の拡大・スキップで隠さず、初回失敗と修正後を記録する。

## 4. スマートフォン・アクセシビリティ

Androidの指描きを主な実機対象にする。iPadの使いやすさの調整を後にする既存の希望を維持し、未確認端末を合格扱いしない。機種・OS・ブラウザー版を記録する。

確認する場面は、320／360／390pxの縦画面、横向き、文字200%、ソフトキーボード、見本／ヒントの開閉、専用画面、ボタン非表示、2本指操作、OSへのPNG取得とZIP保存。説明追加でキャンバスが狭くなったり、周囲へのタッチでページが動いたりしないことを確認する。

工程名・図解の意味をテキストでも伝え、色だけで目印を区別しない。原則44px以上の操作領域、フォーカス順、Escape、シートからの復帰、TalkBack等の読み上げを確認する。自由描画自体はポインター操作が必要という制約を伝える。axeの成功だけで教材の理解や操作性の確認を済ませない。

## 5. 初心者による体験検証の案

**指定**：課題仮説と成功条件を、実際の初心者で検証する。**提案**：最初は少人数（3〜5名を候補）で、指描き未経験者も含める。人数・募集方法・日程・所要時間は未確定。参加や作品の記録を強制せず、画像の取得・共有は別に同意を得る。アプリへの解析・外部送信を追加して代用しない。

### 当日の操作と観察

1. 「好きなキャラクターの正面顔を、描けるところまで試してください」と伝え、最初は操作説明を足さずに観察する。止まった場所と、必要だった手助けを記録する。
2. 画像を選ぶ／使わない、観察する特徴を選ぶ、輪郭やパーツを試す。描く量を指定せず、難しければヒントや中断を使ってもらう。
3. 見本を閉じる、支援を減らす、表情や髪などを変える操作を、本人が望む場合に試してもらう。ヒントを減らさなかったことを失敗扱いしない。
4. 途中でも保存し、一度離れて同じ作品・工程へ戻る。なぞった作品は内部で見返し、対象外の本人の作品では希望すればPNGを端末で開く。なぜ出力可否が違うか分かるかも確認する。
5. 振り返りは1問ずつ、答えない選択も含めて試してもらう。最後に、分かりにくかった操作や不要だった選択肢を尋ねる。

### 記録の観点

| 観点       | 中立的な問い・観察例                                                                         |
| ---------- | -------------------------------------------------------------------------------------------- |
| 始めやすさ | 次の操作を自分で見つけられたか。どこで手が止まったか。説明を探す負担はあったか               |
| 本人の成果 | 「今回どんなものを描いた？」。顔の一部、好きな特徴、初めて試した線など、本人の言葉を記録する |
| 楽しさ     | 「描いていて、どんな気持ちだった？」。楽しくない・分からない・特にないも同じ扱いにする       |
| 発見       | 「何か気づいたことはあった？」。教材の意図する答えを誘導しない                               |
| 技術の学び | 使った目印や省略の方法を説明できるか。希望する別の表情などに、自分で使えるか                 |
| 選べる感覚 | 中断、自由創作、詳しいヒント、比較・質問を使わない選択が理解できたか                         |
| 次の創作   | また描きたいと思うか、何を描いてみたいか。再開しない回答の理由も本人が話したい範囲で聞く     |

**仮説**：同じ工程で複数人が迷う場合は、文章や選択肢・図解・ボタン位置の見直し候補とする。所要時間は観察するが、制限時間や利用者の成績にはしない。目標値・合格率は初回の観察後に提案し、まだ数値で確定しない。

### 後日の確認

本人が同意した場合に限り、後日、自分から再び描いたか・別の絵に方法を使ったかを確認する案とする。「描きたい」という当日の回答と、実際の行動を区別する。自己申告と観察できた行動も区別する。アプリの通知や連続日数の報酬を追加しない。未参加・未回答を離脱や失敗と断定しない。

## 6. 結果の記録と公開判断

各結果に、実施日・対象コミット／教材版・工程・端末・期待と実際・成功／失敗／未実行・必要だった手助け・残課題を記録する。作品を評価点やランキングへ変換しない。画像を記録しない参加者については匿名の操作メモで確認する。

機能上のデータ消失・画像の無断送信・原子的でない移行などの重大な不具合が残る場合は、講座の公開を保留する。初心者の多くが同じ地点で止まる場合は、機能テストが成功していても体験の修正対象とする。未確認の実機や学習効果を、公開可能という判断に含めない。

C1〜C2の途中確認、C3での中断復帰、C4の任意機能、C5の体験結果を分けて報告する。今回の作業ではMarkdownの整合・リンク・アプリ未変更を確認するだけであり、この受け入れ試験を実行したことにはしない。
