## 依存関係と保存の扱い

基本はC1→C2→C3→C4→C5。C4を初回公開から外す場合も、C5ではC1〜C3と既存の任意比較・取込を回帰確認する。

C1〜C2は検証用段階で、講座進行の永続化は未実装と明示する。作品自体の既存保存・再開は維持し、未対応の進行データを既存ストアへ仮保存しない。中断復帰ができる講座として公開するのはC3の保護・バックアップまで確認してからとする。

本設計のうちC3は、追加の画面以上に保存への影響が大きい。C1前に関連先と必要項目をレビューし、C3前に以下を具体化する。

1. D2の記録方式を選び、読取専用PNGと編集可能な主作品を明確に分ける。
2. 実装時点のDB／ZIP版と参照関係を確認し、移行・拒否条件・復元・削除の仕様を先に固定する。
3. PNGの準備後、作品・進行位置・記録を同じ保存キューとトランザクションで整合させる。古い保存の完了で工程や絵を巻き戻さない。
4. 一つの工程記録を更新する確認、失敗時の再試行、PNG退避と未保存表示を用意する。
5. 古いアプリによる講座情報の欠落、未知の教材版・破損した関連、50MiBに近いZIPを検証する。
6. 教材となぞった作品を含む個人用ZIPを例外にするか（D11）と、なぞり描きの識別・旧作品・取込の扱い（D12）を決める。教材・対象作品・それ以外の本人の作品を区別し、制作・詳細・専用画面・保存失敗時・工程画像で同じ出力方針を適用する。コピー、下絵解除、レイヤー操作、復元でも利用範囲を失わない。

## 実装前の判断の順序

- **C1前**：任意の講座を足す方向（D1）、初回にAIを含めるか（D3）、アプリ内描画を主経路にするか（D6）、初回公開に含める範囲（D7）。推奨は既存Canvas＋固定教材。
- **C2前**：汎用教材の図柄・制作・確認担当（D8）。説明量と長さ（D4）は暫定のまま試す。
- **共有制限・移行の実装前**：D10の指定に沿い、個人用ZIPの例外（D11）と識別・旧作品・取込の扱い（D12）を確定し、既存データを保持する変更手順を示す。
- **C3前**：工程記録の閲覧／編集範囲と枚数（D2）、保存設計と形式版。共有制限の対象にPNG退避を提供しない。
- **C4前**：比較方法（D5）、取込後の継続先・応用コピー（D6・D7）。
- **C5で見直す**：各工程の長さ、ヒントを探す負担、指描きで止まる地点。追加講座等（D9）は結果を受けて別に検討する。

## 生成AIを採用する場合の別工程

採用を決めた場合だけ、提供元・モデル・送信項目・同意・予算を確定し、小さな試験を行う。秘密鍵をサーバー側へ置き、文章のみの相談から検証する提案。現在工程への適合、説明の分かりやすさ、断定や採点をしないこと、料金上限、誤った回答、通信失敗でも固定ヒント・作品保存へ戻れることを確認する。外部APIを入れるだけで支援が有効になったとは判定しない。

画像認識・添削・個別カリキュラムはさらに別判断。ログイン・SNS・課金の追加をこの工程へ混ぜない。

## 今回行ったことと行っていないこと

企画とコードを照合し、3種類の講座設計文書とAGENTSの基本原則、既存資料への参照を整える。Markdownの参照先と差分を確認する。アプリコード・教材画像・DB・依存関係・公開ワークフローの変更、講座やAIの実装、新しい機能のブラウザー動作確認は行わない。過去のM16のテスト結果を講座の成功として流用しない。
