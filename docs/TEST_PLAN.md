# 動作確認と受け入れ基準

## 現在の状況

M1〜M6を実装。M2〜M5はユーザーから基本操作の確認報告あり。端末・OS・画像形式・読み上げ等の詳細は未記録。M5の「スキップで閉じる」という指摘を受けて質問を飛ばす操作へ修正し、M6を追加した。今回の修正とM6の実機受け入れは確認待ち。M7は未着手。過去の工程別記録と最新結果を区別する。

## 検証方法

- 単体：候補・質問選択、入力検証、revision、バックアップ形式。
- 結合：実ブラウザーのIndexedDBで保存・復帰・トランザクション失敗・移行・関連削除を確認。モックだけで保存成功としない。
- E2E：Playwrightで主要フローと静的ビルドを確認。描画後の画素、消しゴム、保存前後の画像内容も確認し、スクリーンショットだけに依存しない。
- 手動：実機の描画感、取込、回転、ソフトキーボード、書出、読み上げ。端末エミュレーションを実機確認の代わりにしない。

## アクセシビリティと表示

キーボードでフォーム・テーマ・道具・保存・取込・ギャラリー・データ管理を操作する。フォーカス順、見えるフォーカス、Escape、ダイアログの保持と復帰を確認。VoiceOverまたはTalkBackでラベル・エラー・保存通知を確認する。自由描画はポインター前提という制約を明記する。

320／375／390／768／1280px幅、縦横回転、200%拡大、ソフトキーボード表示で重要操作が使えること。通常文字4.5:1以上などのコントラスト、色以外の状態表示、原則44px以上の操作領域を確認する。意味や文言は手動レビューする。

## 端末・性能

iOS SafariとAndroid Chrome各1台以上、および対象PCブラウザーで必須フローを確認し、機種とバージョンを記録する。利用できない端末は未実行。HTTPS静的配信・サブパス・直接URL再読込も確認する。

M4で基準端末を決め、連続5分描画、20ストローク後の予算内の取消（960pxでは9操作）、回転、保存復帰でクラッシュ・線の欠落がないことを必須とする。入力から反映まで95パーセンタイル50ms以内を暫定目標として計測する。960px作品50件の一覧で原寸画像を全件同時デコードせず、サムネイルを使う。バックアップ上限付近の応答性・容量・失敗回復を測り、必要なら仕様上限を調整する。

375×812px表示のLinux Chromiumで、マウスによる1,115ストロークを300.228秒間繰り返した。20秒ごとに保存revisionが増加し、画像資産が作品画像・サムネイルの2件のまま入れ替わることを確認。描画終了後はrevision45。9回取消後の再保存・再読み込みで全画素一致、未処理エラー0件。

### 性能と検証上の制約

- 960pxの保存済み作品を50件用意し、一覧は12件ずつ表示。初回に読む画像は表示ページのサムネイル以下で、ページ切り替えでも原寸画像や画像ストアの全件取得は0回。
- 約48.98MiBのPNGを含むZIPを生成・検証・追加復元し、すべての画像SHA-256が一致した。最終の全体テストでは作成553ms、選択から検証1,340ms、追加55ms、16ms間隔のUI確認タイマーの最大間隔70.5ms（116回）。測定値はこのクラウドのChromiumでの一例で、スマートフォンの性能保証ではない。
- 大容量ファイル選択は端末上のファイルパスを使う。50MiBを自動操作プロトコル経由でBase64転送する方法では、ファイル投入自体に約5秒の停止が入り、利用者のファイル選択とは異なるため性能計測から除いた。ZIPの検証や画像一致の確認を省略したわけではない。
- 計測ファイルはテスト実行時の`test-results/.../backup-performance.json`へ出力する。テスト生成のランダム画像だけを使い、ユーザーの画像を取り出していない。
